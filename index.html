00 How it works

Two independent mode systems run simultaneously. Brand modes control how it looks. Layout modes control how it scales.

LAYER 1
Primitives
Raw values — hex colours, px numbers, font strings. No semantic meaning. Hidden from pickers.
LAYER 2
Semantic collections
Alias Primitives with meaning. Brand modes (ADR · ExOz · RB · LA · Base) + Layout modes (Expanded · Compact). Applied independently on the same frame.
LAYER 3
CSS export
CSS custom properties are output per brand via a class on <html>. Media query or .compact class handles breakpoints. Export pipeline TBD once component library is stable.
01 Spacing scale

Semantic/Layout · 8pt grid · foundational scale for all padding, margin and gap. Adoption is mechanical — pick the size, use the token.

How Expanded vs Compact works in code
Each token has two CSS variable names — a base name for desktop and a -compact suffix for mobile. During migration, components opt in individually: use var(--spacing-m) on desktop and var(--spacing-m-compact) inside a breakpoint or .compact class. In v2, both will collapse into a single token driven by a global media query override.

      10
      Token mapping — v1 Confluence → v2 Design system
    

    
How existing Confluence tokens map to the new system, and what's been added and why. The core shift: v1 names things by what it looks like. v2 names things by what it does.


    

      The structural problem with v1: tokens like --brand-primary are used for both button backgrounds and text colour in different components. When a whitelabel sets their primary colour, text layered on top becomes unreadable because nothing in the system guarantees contrast. v2 solves this structurally — not by checking, but by making it impossible to misuse.
    


    
    

      
Colour

      

        

          v1 Confluence token
          v2 Design system token
          Why the change
          Status
        

        
          

            --brand-primary
            surface/brand
            --brand-primary was used for both button fills and text colour — impossible to know if a swap breaks contrast. surface/brand is explicitly a background fill token only. The companion text/on-surface-brand always tells you what's safe to put on top of it.
            Mapped
          

          

            —
            surface/brand-dark
            No equivalent in v1. Dev was darkening --brand-primary arbitrarily or reusing --brand-secondary (a dark neutral, not a dark brand). Powers button hover states and dark hero gradient overlays.
            New
          

          

            --bg-white
--bg-primary-grey		
            surface/page
surface/card
surface/bg		
            v1 uses literal colour names — --bg-white breaks the moment a whitelabel wants a warm off-white page. surface/page describes intent — the actual colour is set per brand in the mode. No code changes needed for a whitelabel to customise.
            Mapped
          

          

            —
            text/on-surface-brand
            The most critical new token. Directly solves the SkyBus/DreamWorld whitelabel contrast bug. When a brand sets surface/brand, this token tells any component what text colour is guaranteed readable on top — per brand. ExOz: black on yellow. Adrenaline: charcoal on cyan. RedBalloon: white on red. Without it, the platform guesses — which is why the bug keeps happening.
            New
          

          

            --text-primary-light
            text/secondary
            text-primary-light implies it's a lighter version of primary — but it's actually used for supporting copy, labels, and muted UI. secondary matches intent and aligns with industry convention (Material, Radix, Tailwind).
            Mapped
          

          

            —
            text/brand
            No coloured text token in v1 at all. Dev was using --brand-primary for coloured links and price highlights — the same variable as button fills. Adrenaline uses their blue for text/brand (not orange) because orange text on white fails contrast.
            New
          

          

            --border-primary
(maps to --bg-black)		
            border/brand
border/success
border/warning
border/error		
            v1 has one border token (black). No semantic borders at all. Without these, input validation states, selected card outlines, and focus rings are hardcoded or misuse brand variables.
            New
          

          

            —
            icon/default
icon/muted
icon/inverse
icon/brand		
            No icon tokens in v1. Icons currently inherit text colour or are hardcoded fills. These tokens let icons respond to brand mode switching automatically without per-component overrides.
            New
          

          

            —
            interactive/brand-hover
interactive/brand-pressed		
            No interactive state tokens in v1. Hover and pressed states are hardcoded hex values or not implemented. Formalises the pattern Smarajit already built in primitives (e.g. colour/adr/charcoal-hover) into semantic tokens any component can reference.
            New
          

          

            --ui-red
--ui-green
--ui-blue		
            status/error-bg + status/error-text
status/success-bg + status/success-text
status/warning-bg + status/warning-text		
            v1 defines one colour per state. Our status tokens split each into a background (light tint) and foreground (readable text on that tint) — so an error toast uses status/error-bg as fill and status/error-text as label. Contrast is guaranteed by design.
            Mapped
